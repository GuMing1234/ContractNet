# ContractNet 项目策划书

> 文档类型：**项目策划与组织方案**
> 配套：《详细设计文档》（`docs/design.md`）
> 团队规模：8 人 ｜ 周期：10 周（含 1 周 buffer）
> 版本：v1.0 ｜ 2026-11-16 ｜ 负责人：项目 lead

---

# 1. 项目目标与成功标准

## 1.1 我们要交付什么

| 交付物 | 判定标准 | 谁验收 |
|---|---|---|
| **A. 能跑的系统** | 3 个基准任务端到端跑通（W8） | 全组 Demo |
| **B. 可复现的数据** | 3 基准 × 5 重复的对比表 | 负责人核对原始日志 |
| **C. 能讲的故事** | 每人能讲清自己模块的 5 个决策 | 相互抽查 |
| **D. 开源仓库** | 别人能按 README 在 30 分钟内跑起来 | 找一个外人试 |

## 1.2 明确不追求

- ❌ 不做通用框架 / SDK
- ❌ 不做生产级安全沙箱
- ❌ 不和商业框架比性能
- ❌ 不追求代码量（追求"每块都能讲清为什么"）

> **一句话**：我们要的是「**可解释的完成度**」，不是「代码行数」。

# 2. 组织架构

## 2.1 分组原则（三条）

| 原则 | 说明 |
|---|---|
| **按模块分人，不按阶段轮换** | 每人深耕 1–2 个模块。轮换会导致全组半懂 |
| **按接口面切，不按文件切** | 两人改同一文件的成本，远高于两人各改一组独立模块 |
| **关键路径双人** | R1 / R4 / R6 三个最关键的模块配 backup，防掉线 |

## 2.2 八个角色

| 角色 | 代号 | 负责模块 | 文件 | 关键路径 |
|---|---|---|---|---|
| **架构与契约** | **R1** | Types + Orchestrator | `core/types.py` `core/orchestrator.py` | ⭐⭐⭐ |
| **任务分解** | **R2** | Planner | `core/planner.py` | ⭐ |
| **竞标仲裁** | **R3** | Auctioneer | `core/auctioneer.py` | ⭐ |
| **Agent 运行时** | **R4** | Agent + ReAct | `core/agent.py` | ⭐⭐⭐ |
| **工具与网关** | **R5** | Sandbox + LLMGateway | `tools/sandbox.py` `llm/client.py` | ⭐⭐ |
| **质量门控** | **R6** | QualityGate | `core/quality_gate.py` | ⭐⭐⭐ |
| **冲突与存储** | **R7** | Conflict + StateStore | `core/conflict.py` `memory/store.py` | ⭐⭐ |
| **观测与评估** | **R8** | Tracer + Eval | `observability/` `eval/` | ⭐⭐ |

> **负责人 = R1 + PM**。R1 的工作量最大但最需要全局视野，适合负责人；
> 但**必须配 backup 分担 orchestrate 的联调工作**（建议 R4 或 R6 兼）。

## 2.3 角色卡片

### R1 · 架构与契约（负责人兼）

| 项 | 内容 |
|---|---|
| **负责** | 全项目数据结构定稿、主循环、状态机、并发控制、集成联调 |
| **核心交付** | ① `types.py` 五个模型定稿 ② 主循环能并发跑 ③ 状态转移可回放 ④ 全组 code review |
| **前置知识** | Pydantic discriminated union、`ThreadPoolExecutor`、状态机设计 |
| **节奏** | W1 模型+骨架 → W2 主循环 → W4 并发 → W7 回放 |
| **简历 story** | 「我设计了整个系统的数据契约与状态机，并主持了接口冻结」 |
| **风险** | 一个人懂全局 → 必须有文档沉淀（详设文档就是他写的） |

### R2 · 任务分解

| 项 | 内容 |
|---|---|
| **负责** | 目标 → 子任务 DAG；失败后的重新分解 |
| **核心交付** | ① LLM 分解 + 后处理校验（无环、粒度、数量） ② 四种重规划策略 |
| **前置知识** | 结构化输出、prompt 设计、拓扑排序、DFS 环检测 |
| **节奏** | W1 读骨架 → W3 LLM 分解 → W5 重规划 |
| **简历 story** | 「我做了 LLM 驱动的任务分解，并把不可靠的 LLM 输出变成了可靠的 DAG」 |
| **难点** | LLM 输出不稳定 → 必须四层兜底：prompt 约束 / 解析容错 / 结构校验 / 规则补位 |

### R3 · 竞标仲裁

| 项 | 内容 |
|---|---|
| **负责** | 契约广播、Bid 收集、综合评分、授标、无竞标处理 |
| **核心交付** | ① 两阶段筛选（零成本预筛） ② 加权评分函数 ③ 无竞标重发 |
| **前置知识** | 加权评分设计、简单统计（EMA 成功率） |
| **节奏** | W1 读骨架 → W3 评分函数 → W4 无竞标处理 |
| **简历 story** | 「我用竞标协议替代静态指派，并把评分函数从调参问题变成了可解释的两阶段筛选」 |
| **难点** | 权重怎么定？→ 不要"调参"，要能说清每个权重的物理意义 |

### R4 · Agent 运行时

| 项 | 内容 |
|---|---|
| **负责** | Agent 基类、竞标逻辑、ReAct 执行循环、工具调用编排 |
| **核心交付** | ① 能跑多轮工具调用的 ReAct 循环 ② 能力/置信度计算 ③ 执行记录 |
| **前置知识** | OpenAI function calling 协议、多轮消息结构 |
| **节奏** | W1 读骨架 → W3 ReAct 循环 → W4 工具链调通 |
| **简历 story** | 「我实现了 ReAct 执行引擎，处理了工具调用的错误回传与最大步数保护」 |
| **难点** | assistant 消息回填 tool_calls 的格式（错一个字段就 400） |

### R5 · 工具与网关

| 项 | 内容 |
|---|---|
| **负责** | 工具沙箱（权限/超时/截断）、LLM 网关（重试/缓存/录制/预算/归因） |
| **核心交付** | ① 3 个内置工具可用 ② 网关支持回放模式 ③ 按模块 token 归因 |
| **前置知识** | `subprocess`、路径安全、指数退避 |
| **节奏** | W1 网关基础 → W3 沙箱 → W6 缓存与录制 |
| **简历 story** | 「我做了 LLM 网关，让整个团队的测试不花一分钱（录制回放），并实现了按模块的成本归因」 |
| **价值** | **这个角色直接决定全组的 token 账单**，别轻视 |

### R6 · 质量门控

| 项 | 内容 |
|---|---|
| **负责** | 三层校验（格式/语义/影响）、结构化反馈、裁判接入 |
| **核心交付** | ① 按产物类型分派的 L1 ② LLM 裁判 + 健壮解析 ③ 影响校验 |
| **前置知识** | `jsonschema`、`ast` 模块、LLM-as-Judge 的偏差 |
| **节奏** | W1 读骨架 → W5 三层 → W6 裁判校准 |
| **简历 story** | 「我设计了按产物类型分派的三层门控，并处理了 LLM 裁判输出不可解析的问题」 |
| **难点** | 代码产物不是 JSON —— **这是最容易写错的地方** |

### R7 · 冲突与存储

| 项 | 内容 |
|---|---|
| **负责** | 五种冲突检测、五种消解策略、状态存储、回放 |
| **核心交付** | ① 文件冲突 + 死锁检测 ② AST 接口对比 ③ 事件表可回放 |
| **前置知识** | `ast` 模块、DFS 找环、wait-for graph、SQLite |
| **节奏** | W1 内存存储 → W6 冲突检测 → W7 持久化+回放 |
| **简历 story** | 「我实现了多 Agent 冲突检测，覆盖文件写冲突、接口不一致与死锁」 |
| **价值** | **这是本项目最核心的差异化模块**，也是最容易讲出深度的一块 |

### R8 · 观测与评估

| 项 | 内容 |
|---|---|
| **负责** | trace 与日志、指标采集、基准任务集、对比实验、Dashboard |
| **核心交付** | ① span 树 ② 5 组指标 ③ 3 个基准任务 ④ 对比报告 |
| **前置知识** | 结构化日志、统计基础（中位数/分布）、Streamlit |
| **节奏** | W1 日志 → W4 span → W8 基准与报告 |
| **简历 story** | 「我搭建了评估体系，用 3 个基准 × 5 次重复产出了可复现的对比数据」 |
| **重要** | **简历上的数字由这个人产出**，不能分配给划水的人 |

## 2.4 关键路径与备份

```
关键路径（延迟 = 全项目延迟）
  R1（契约/主循环） → R4（执行） → R6（门控） → R7（冲突）
```

| 主 owner | backup | 为什么 |
|---|---|---|
| R1 | R4 | 主循环与执行天然接壤 |
| R4 | R5 | 工具链与执行接壤 |
| R6 | R8 | 门控结论要靠观测验证 |
| R7 | R3 | 冲突检测与仲裁都要读 DAG |

**backup 的义务**：不是"等 owner 掉线才管"，而是
- 读过 owner 的代码
- 能跑通 owner 的测试
- 在 owner 的 PR 上做过 at least 1 次 review

# 4. 协作机制

## 4.1 每周组会（60 分钟，固定议程）

**时间**：每周五晚（固定，不改期）
**主持**：负责人
**必须到场**：全员（不能到要提前在群里说，并提交书面周报）

### 议程

| 时长 | 环节 | 具体做法 |
|---|---|---|
| **0–5** | 上周回顾 | 负责人念 `TASKS.md`：上周承诺的任务，完成了几个、没完成是哪几个 |
| **5–35** | **每人 3 分钟 Demo** | **必须现场跑**，不许说"我写完了"。跑不了就当场说卡在哪 |
| **35–45** | 卡点攻关 | 只讨论"卡了超过 2 天的问题"，其他问题线下解决 |
| **45–55** | 下周认领 | 对着 `TASKS.md` 的空行，**当场认领当场记名字** |
| **55–60** | 风险与协调 | 有没有人要掉线、有没有人需要支援、有没有接口要改 |

### 三条会场纪律

1. **不汇报态度，只汇报状态**：「我很努力」没有意义，「这个能跑」才是有意义的
2. **不讨论超过 3 分钟跑偏的话题**：负责人负责打断，「这个线下单独聊」
3. **不追责，只追事实**：「为什么没做」→「卡在哪」

## 4.2 会前必须交的东西（每人 3 行）

**开会前 1 小时，每人在群里发这三行：**

```
【上周做了什么】<一句话，能对应 TASKS.md 的编号>
【本周要做什么】<一句话>
【卡在哪】<没有就写"无">
```

**为什么只要求 3 行**：要求写长文，就没人写。
**为什么必须有第三行**：前两行是汇报，第三行才是求助。

## 4.3 任务卡模板

每个任务在 `TASKS.md` 里必须有这四行，缺一不可：

```markdown
| 编号 | 任务 | 负责人 | 验收标准 |
| 3.1 | planner 改成 LLM 分解 | 张三 | 跑 `pytest tests/test_planner.py` 全绿，且给一句中文目标能拆出 3~8 个无环子任务 |
```

**验收标准的三条要求**：

| 要求 | ❌ 反例 | ✅ 正例 |
|---|---|---|
| 可执行 | 「分解功能完善」 | 「跑 XXX 命令，输出 YYY」 |
| 可判定 | 「效果还不错」 | 「子任务数在 3~8 之间」 |
| 与任务相关 | 「代码质量好」 | 「无环」 |

## 4.4 `TASKS.md` 使用规则

| 规则 | 说明 |
|---|---|
| **认领制** | 谁认领谁负责，写上名字就是承诺 |
| **一次只做一件** | 一个人同时挂 3 个"进行中"= 一个都没在推 |
| **完成 = 验收通过** | 不是"我写完了" |
| **每周五清空"待审"** | 拖着不审的 PR 会让作者失去动力 |

## 4.5 每周的周五仪式（30 分钟，负责人单独做）

```
1. 对照 TASKS.md，统计：承诺 N 个，完成 M 个
2. 完成率 < 60% → 下周任务量砍半（不是加压，是现实调整）
3. 把本周教训写 3 行进 docs/weekly/W{n}.md
4. 更新 design.md 里被证伪的设计（如果有）
```

> **完成率低不要加任务，要减任务。** 加任务是新手 PM 最常犯的错。

# 5. 交付标准（如何判断"做完了"）

## 5.1 三件套

任何交付必须有：

| # | 交付什么 | 例 |
|---|---|---|
| 1 | **能跑的东西** | 一条命令能跑出结果 |
| 2 | **怎么验证** | 命令 + 预期输出 |
| 3 | **一段自述**：改了什么 / 为什么 / 踩了什么坑 | 写进 PR 或 `docs/decisions/` |

> 第 3 条是最强的过滤器：**代码可以抄，"踩了什么坑"抄不了。**

## 5.2 三个档次的完成度

| 档次 | 定义 | 是否可接受 |
|---|---|---|
| 🟢 完成 | 功能可用 + 有测试 + 有验证说明 | 是 |
| 🟡 可用未完善 | 功能可用，测试少量，有 TODO 标注 | **是**（学生项目正常） |
| 🔴 未完成 | 跑不起来 / 无法验证 | 否 |

> **我们接受 🟡，不接受 🔴。**
> 「粗糙但完整」远好于「精致但跑不起来」。

## 5.3 红牌清单（当场打回）

| 情况 | 处理 |
|---|---|
| PR 没写"怎么验证" | 打回 |
| 出现 `except: pass` | 打回 |
| 说"做完了"但说不出改了哪 | 打回，当场打开 diff 讲 |
| 连续两周 Demo 没东西 | **私下**聊一次，公开不说 |
| 偷偷改 `types.py` | 打回 + 群里提醒 |

## 5.4 绿旗（公开表扬）

| 情况 | 处理 |
|---|---|
| PR 里主动写"我踩了什么坑" | 会上念出来，让全组学这个格式 |
| 主动帮别人 review | 记功，下次他的 PR 优先审 |
| 发现别人模块的 bug | 记功，且这个 bug 归**发现者**写进简历 |

# 6. 人员风险管理

## 6.1 现实预期

> 8 个大二学生，**一定会有 1～2 人掉线或半掉线**。这是概率，不是失败。

所以设计目标是：
- 让认真的人**有回报**（简历素材归他、Demo 由他讲）
- 让掉线的人**不拖累**（关键路径不放他手里）
- 让问题**早暴露**（每周公开 Demo，不拖到第 6 周）

## 6.2 掉线的三级处理

| 级别 | 表现 | 处理 |
|---|---|---|
| **L1 慢** | 进度落后但在动 | 减任务量，配对帮忙 |
| **L2 卡** | 一周没进展 | 负责人 30 分钟一对一，问清卡点 |
| **L3 失联** | 连续两周无产出 | **把模块整体转给 backup**，公开说明，不指责 |

> 转到 L3 时**必须公开说明**（否则 backup 会觉得被惩罚）。

## 6.3 负责人自己不踩的三个坑

| 坑 | 表现 | 正确做法 |
|---|---|---|
| **全包** | 「我自己写更快」 | 前两周快，第八周累死且无人接手 |
| **只问进度** | 「做完了吗」 | 问「卡在哪」 |
| **加任务** | 完成率低就加人加任务 | 完成率低就**减任务** |

# 8. 一页纸总结

```
目标：8 周做出 MVP，10 周交出可开源项目 + 可复现数据
组织：按模块分 8 个角色，关键路径配 backup，每人不轮换
冻结：W2 接口冻结，8 人能白纸画图才准开工
```
