# 1. 项目目标与成功标准

## 1.1 交付内容

| 交付物 | 判定标准 | 验收方式 |
| ------------- | ----------------------- | --------- |
| **A. 可运行系统** | 3 个基准任务端到端跑通（W8） | 周会现场演示 |
| **B. 可复现数据** | 3 个基准 × 5 次重复的对比结果 | 负责人核对原始日志 |
| **C. 可陈述的成果** | 成员可说明本模块的 5 项关键设计决策 | 交叉抽查 |
| **D. 开源仓库** | 外部人员按 README 可在 30 分钟内完成部署 | 由团队外成员试行验证 |

## 1.2 非目标

- ❌ 不做通用框架 / SDK
- ❌ 不做生产级安全沙箱
- ❌ 不以性能指标对标商业框架
- ❌ 不以代码规模为目标（以模块级可解释性为目标）

> **验收取向**：以「可解释的完成度」为交付标准，不以代码规模作为衡量依据。

# 2. 组织架构

## 2.1 分组原则（三条）

| 原则               | 说明                                |
| ---------------- | --------------------------------- |
| **按模块分人，不按阶段轮换** | 每人长期负责 1–2 个模块；轮换会导致成员对各模块均缺乏深入理解 |
| **按接口面切，不按文件切**  | 两人改同一文件的成本，远高于两人各改一组独立模块          |
| **关键路径双人**       | R1 / R4 / R6 三个关键模块设置备份人，降低单点缺失风险 |

## 2.2 三个协作小组

> 目的：把 R1–R8 按**协作紧密度**聚成三条链，让组内先消化接口分歧，减少跨组往返。
> 它**不改变角色分工**，只改变沟通路径；每人的模块职责仍以 §2.3 为准。

| 组 | 成员 | 为什么绑在一起 |
|---|---|---|
| **A · 编排链** | R1（负责人）、R2 planner、R3 auctioneer | 三者都在读写同一个 `TaskDAG` 与 `Contract`，任一字段变动会同时影响三人 |
| **B · 执行链** | R4 agent、R5 tools/llm、R6 quality_gate | 决定「一次执行能不能跑通」：R5 提供能力，R4 执行，R6 判定 |
| **C · 支撑链** | R7 conflict/store/memory、R8 tracer/eval | 都服务于前两条链，且都涉及「数据怎么存、怎么看」 |

### 组内联络人

每组设一名**接口联络人**（不称组长）：

| 组   | 联络人      | 理由                  |
| --- | -------- | ------------------- |
| A   | R1（负责人兼） | 契约源头在此，无需另设         |
| B   | **R4**   | 处于执行链链头，且属关键路径      |
| C   | **R7**   | 处于关键路径末端，且与 R3 互为备份 |

### 联络人的职责边界

**只做两件事**：

1. **组内接口先对齐，再上报** —— 同组三人对同一接口有分歧时，先内部讨论出结论，再交负责人裁定
2. **组员卡住时是第一响应人** —— 组员阻塞超过 30 分钟，首位求助对象是联络人而非负责人

**明确不承担**：

| ❌ 不做 | 原因 |
|---|---|
| 代组员汇报进度 | 进度一律由本人每日在群里报三行，转述会丢失信息 |
| 代组员编写代码 | 会让联络人成为瓶颈，其他成员反而掉队 |
| 代替负责人做进度考核 | **产出验收由负责人直接对每个人，不经过中间层** |
| 催促组员 | 联络人是服务角色，不是管理角色 |

### 联络人的人选标准

按以下顺序判断，**不以技术最强为标准**：

1. 群内响应及时 —— 组员求助不会被搁置
2. 已提交过可运行的代码 —— 说明确实在动手
3. 能判断「接口是否对齐」即可，不要求承担最复杂的部分

### 各阶段的作用

| 阶段     | 联络人的主要作用                   |
| ------ | -------------------------- |
| W1–W2  | 组织组内接口对齐（**W2 冻结前必须完成一次**） |
| W3–W6  | 兼任组员阻塞的第一响应人               |
| W7–W8  | 组织组内联调，负责人只看结果             |
| W9–W10 | 汇总本组的文档与演示材料               |

> **检查点**：W3 结束时，若某位联络人一次都未组织过组内讨论，应更换人选。

## 2.4 角色卡片

### R1 · 架构与契约（负责人兼）

| 项         | 内容                                                                         |
| --------- | -------------------------------------------------------------------------- |
| **负责**    | 全项目数据结构定稿、主循环、状态机、并发控制、集成联调                                                |
| **核心交付**  | ① `types.py` 五个模型定稿 ② 主循环能并发跑 ③ 状态转移可回放 ④ `EventBus` 抽象定稿 ⑤ 全组 code review |
| **前置知识**  | Pydantic discriminated union、`ThreadPoolExecutor`、状态机设计                    |
| **节奏**    | W1 模型+骨架 → W2 主循环 → W4 并发 → W7 回放                                          |
| **可陈述贡献** | 「我设计了整个系统的数据契约与状态机，并主持了接口冻结」                                               |
| **风险**    | 一个人懂全局 → 必须有文档沉淀                                                           |

### R2 · 任务分解

| 项         | 内容                                                     |
| --------- | ------------------------------------------------------ |
| **负责**    | 目标 → 子任务 DAG；失败后的重新分解                                  |
| **核心交付**  | ① LLM 分解 + 后处理校验（无环、粒度、数量） ② 四种分解策略（初次 / 细化 / 合并 / 增量） |
| **前置知识**  | 结构化输出、prompt 设计、拓扑排序、DFS 环检测                           |
| **节奏**    | W1 读骨架 → W3 LLM 分解 → W5 重规划                            |
| **可陈述贡献** | 「我做了 LLM 驱动的任务分解，并把不可靠的 LLM 输出变成了可靠的 DAG」              |
| **难点**    | LLM 输出不稳定 → 必须四层兜底：prompt 约束 / 解析容错 / 结构校验 / 规则补位      |

### R3 · 竞标仲裁

| 项         | 内容                                     |
| --------- | -------------------------------------- |
| **负责**    | 契约广播、Bid 收集、综合评分、授标、无竞标处理              |
| **核心交付**  | ① 两阶段筛选（零成本预筛） ② 加权评分函数 ③ 无竞标重发        |
| **前置知识**  | 加权评分设计、简单统计（EMA 成功率）                   |
| **节奏**    | W1 读骨架 → W3 评分函数 → W4 无竞标处理            |
| **可陈述贡献** | 「我用竞标协议替代静态指派，并把评分函数从调参问题变成了可解释的两阶段筛选」 |
| **难点**    | 权重怎么定？→ 不要"调参"，要能说清每个权重的物理意义           |

### R4 · Agent 运行时

| 项         | 内容                                        |
| --------- | ----------------------------------------- |
| **负责**    | Agent 基类、竞标逻辑、ReAct 执行循环、工具调用编排           |
| **核心交付**  | ① 能跑多轮工具调用的 ReAct 循环 ② 能力/置信度计算 ③ 执行记录    |
| **前置知识**  | OpenAI function calling 协议、多轮消息结构         |
| **节奏**    | W1 读骨架 → W3 ReAct 循环 → W4 工具链调通           |
| **可陈述贡献** | 「我实现了 ReAct 执行引擎，处理了工具调用的错误回传与最大步数保护」     |

### R5 · 工具与网关

| 项         | 内容                                                                                         |
| --------- | ------------------------------------------------------------------------------------------ |
| **负责**    | 工具沙箱（权限/超时/截断）、内置工具集、LLM 网关（重试/缓存/录制/预算/归因）                                                |

| **可陈述贡献** | 「我做了 LLM 网关，让整个团队的测试不花一分钱（录制回放），并实现了按模块的成本归因」                                              |

| 项 | 内容 |

## 2.5 关键路径与备份

```
关键路径（延迟 = 全项目延迟）
  R1（契约/主循环） → R4（执行） → R6（门控） → R7（冲突）
```

| 主 owner | backup | 为什么 |
|---|---|---|
| R1 | R4 | 主循环与执行天然接壤 |
| R4 | R5 | 工具链与执行接壤 |
| R6 | R8 | 门控结论要靠观测验证 |
| R7 | R3 | 冲突检测与仲裁都要读 DAG |

**备份人职责**：并非仅在主负责人缺席时介入，而应常态性地：
- 读过 owner 的代码
- 能跑通 owner 的测试
- 在 owner 的 PR 上做过 at least 1 次 review

# 4. 协作机制

## 4.1 每周组会（60 分钟，固定议程）

**时间**：每周五晚（固定，不改期）
**主持**：负责人
**必须到场**：全员（不能到要提前在群里说，并提交书面周报）

### 议程

| 时长 | 环节 | 具体做法 |
|---|---|---|
| **0–5** | 上周回顾 | 负责人宣读 `TASKS.md`：上周承诺任务的完成数量与未完成项清单 |
| **5–35** | **每人 3 分钟演示** | 必须现场运行；不接受口头声明完成。无法运行时须当场说明阻塞点 |
| **35–45** | 阻塞项处理 | 仅讨论受阻超过两日的事项，其余事项会后单独沟通 |
| **45–55** | 下周认领 | 对照 `TASKS.md` 待领条目，**当场认领并登记负责人** |
| **55–60** | 风险与协调 | 有无成员投入度变化、有无成员需要支援、有无接口需变更 |

### 三条会场纪律

1. **不汇报态度，只汇报状态**：「我很努力」没有意义，「这个能跑」才是有意义的
2. **不讨论超过 3 分钟跑偏的话题**：负责人负责打断，「这个线下单独聊」
3. **不作追责性讨论**：聚焦事实与阻塞点，而非原因归属

## 4.2 会前必须交的东西（每人 3 行）

**开会前 1 小时，每人在群里发这三行：**

```
【上周完成】<对应 TASKS.md 编号的简要说明>
【本周计划】<简要说明>
【阻塞点】<如无则写"无">
```

**为什么只要求 3 行**：要求写长文，就没人写。
**为什么必须有第三行**：前两行是汇报，第三行才是求助。

## 4.3 任务卡模板

每个任务在 `TASKS.md` 里必须有这四行，缺一不可：

```markdown
| 编号 | 任务 | 负责人 | 验收标准 |
| 3.1 | planner 改成 LLM 分解 | 张三 | 跑 `pytest tests/test_planner.py` 全绿，且给一句中文目标能拆出 3~8 个无环子任务 |
```

**验收标准的三条要求**：

| 要求 | ❌ 反例 | ✅ 正例 |
|---|---|---|
| 可执行 | 「分解功能完善」 | 「跑 XXX 命令，输出 YYY」 |
| 可判定 | 「效果还不错」 | 「子任务数在 3~8 之间」 |
| 与任务相关 | 「代码质量好」 | 「无环」 |

## 4.4 `TASKS.md` 使用规则

| 规则 | 说明 |
|---|---|
| **认领制** | 谁认领谁负责，写上名字就是承诺 |
| **一次只做一件** | 一个人同时挂 3 个"进行中"= 一个都没在推 |
| **完成 = 验收通过** | 不是"我写完了" |
| **每周五清空"待审"** | 拖着不审的 PR 会让作者失去动力 |

## 4.5 每周的周五仪式（30 分钟，负责人单独做）

```
1. 对照 TASKS.md，统计：承诺 N 个，完成 M 个
2. 完成率 < 60% → 下周任务量砍半（不是加压，是现实调整）
3. 把本周教训写 3 行进 docs/weekly/W{n}.md
4. 更新 04-design.md 里被证伪的设计（如果有）
```

> **完成率偏低时应下调任务量，而非追加任务。** 追加任务是最常见的误判。

# 5. 交付标准（如何判断"做完了"）

## 5.1 三件套

任何交付必须有：

| # | 交付什么 | 例 |
|---|---|---|
| 1 | **能跑的东西** | 一条命令能跑出结果 |
| 2 | **怎么验证** | 命令 + 预期输出 |
| 3 | **变更说明**：改动内容 / 设计理由 / 遇到的主要问题 | 写进 PR 描述或 `docs/decisions/` |

> 第 3 条是有效性最高的判定依据：代码可以被复制，但问题定位与解决过程无法复制。

## 5.2 三个档次的完成度

| 档次 | 定义 | 是否可接受 |
|---|---|---|
| 完成 | 功能可用、具备测试、提供验证说明 | 是 |
| 可用未完善 | 功能可用、测试覆盖有限、待办项已标注 | 是（同类项目常规水平） |
| 未完成 | 无法运行或无法验证 | 否 |

> **判定原则：接受「可用但未完善」，不接受「无法运行」。**

## 5.3 不通过判定

| 情况 | 处理 |
|---|---|
| PR 未提供验证方法 | 驳回 |
| 出现 `except: pass` | 驳回 |
| 声明完成但无法说明改动内容 | 驳回，要求现场演示改动差异 |
| 连续两次周会无演示内容 | 由负责人单独沟通，不在会上公开提及 |
| 未声明修改公共数据结构 | 驳回，并在项目群内通报一次 |

## 5.4 认可项（公开通报）

| 情况 | 处理 |
|---|---|
| PR 中主动记录问题与解决过程 | 会上作为范例说明，推广该写法 |
| 主动评审他人 PR | 记录贡献，其后续 PR 优先评审 |
| 发现其他模块的缺陷 | 记录贡献，该缺陷的发现归属记入发现者 |

# 6. 人员风险管理

## 6.1 现实预期

> 经验上，多人协作项目中通常会出现个别成员投入度阶段性下降的情况。此属常态风险，不作为管理失当的判定依据。

所以设计目标是：
- 使投入充分的成员获得相应回报（项目材料署名、演示由其主讲）
- 使投入度下降的成员不影响整体进度（关键路径不依赖单人）
- 让问题**早暴露**（每周公开 Demo，不拖到第 6 周）

## 6.2 投入度下降的分级处理

| 级别        | 表现      | 处理                          |
| --------- | ------- | --------------------------- |
| **L1 进度滞后** | 有产出但进度落后 | 下调任务量，安排协作支援 |
| **L2 停滞** | 连续一周无进展 | 负责人进行 30 分钟一对一沟通，明确阻塞点 |
| **L3 失联** | 连续两周无产出 | 将该模块整体移交备份人，在会上公示，不作追责表述 |

> 转到 L3 时**必须公开说明**（否则备份人可能将其视为负面处置）。

## 6.3 负责人需规避的三种行为

| 行为 | 表现 | 正确做法 |
|---|---|---|
| **全包** | 「我自己写更快」 | 前期看似提前，后期成为单点瓶颈且无人可接手 |
| **仅询问进度** | 只问是否完成 | 询问阻塞点 |
| **追加任务** | 完成率偏低时追加人力与任务 | 完成率偏低时**下调任务量** |

# 8. 一页纸总结

```
目标：8 周做出 MVP，10 周交出可开源项目 + 可复现数据
组织：按模块分 8 个角色，关键路径配 backup，每人不轮换
冻结：W2 接口冻结，8 人可独立绘图方可进入开发
节奏：周五组会（5'回顾 + 30'演示 + 10'阻塞项 + 10'认领 + 5'风险）
交付：可运行 + 可验证 + 变更说明，三项缺一不可
标准：接受功能可用但未完善的交付，不接受无法运行
不通过：缺少验证 / except:pass / 声明完成但无法说明改动
预期：个别成员投入度可能下降，组织设计须具备容错能力
铁律：完成率偏低时下调任务量，不追加任务
```
