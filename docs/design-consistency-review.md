## 0. 结论摘要

| 维度 | 结论 |
|---|---|
| **方向** | ✅ **完全一致**，三大创新点（契约竞标 / 动态重规划 / 三层门控）全部保留 |

## 7. 偏离清单：分类与处置建议

### 🔴 A 类：必须回补（当前设计完全未覆盖，且属于原设计的核心卖点）

| # | 缺口 | 为什么必须补 | 建议归属 |
|---|---|---|---|
| **A1** | **Agent Memory 模块**（§9） | 原设计把它列为独立模块，"跨任务经验积累"是卖点之一。缺失会导致：`confidence` 无历史来源、失败模式无法复用、Agent 每次从零开始 | R7 或 R4 |
| **A2** | **`eval/metrics.py` + `eval/runner.py`**（§13） | 没有它就没有对比数据；没有数据，项目只能讲"机制"不能讲"效果" | R8 |
| **A3** | **`tools/builtins.py` 内置工具集** | Agent 的 ReAct 循环需要一个明确的工具清单与权限表，否则执行层无法验收 | R5 |
| **A4** | **"合并（升级）"重规划策略** | 原设计明确列为三大策略之一（"合并多个子任务给单个 Agent 减少协调开销"）。缺失则重规划只有"拆"没有"合" | R2 |

### 🟡 B 类：建议补齐（影响可维护性与可验收性）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| **B1** | `ContractManager` 未独立 | 契约构造与生命周期散落在 Orchestrator 内，难单测 | 抽成轻量类（约 60 行） |
| **B2** | `Executor` 未单列 | 并发控制逻辑无处安放，验收标准不明确 | 在 §5.4 内明确为子组件 |
| **B3** | 「增量分解」策略（执行中插入新任务） | 场景 S2（数据分析发现缺数据）依赖它 | 列为 W7 增强项或明确舍去 |
| **B4** | 模块间依赖矩阵 | W2 分工需要它判断谁可并行开工 | W2 产出 |
| **B5** | 「步骤效率」指标定义 | 原设计五大指标之一，缺它则评估不完整 | §9.2 补定义 |

### 🟢 C 类：合理偏离（不必回补，仅需在文档中说明理由）

| # | 偏离 | 理由 |
|---|---|---|
| C1 | Anthropic SDK 未纳入 | 统一走 OpenAI 兼容接口，换厂商只改 `base_url` |

| C4 | `types.py` 合并原 `contract.py` | 减少文件跳转，模型集中便于冻结 |

## 8. 当前设计相对原设计的 5 处改进

这 5 处是原设计中会导致实现失败、但文档未预见的问题，当前设计已修正：

| # | 原设计的问题 | 当前设计的修正 | 依据 |
|---|---|---|---|
| 1 | `Contract` 无 `task_type` 字段，能力匹配只能对任务描述做子串匹配 | 字段必带，见 ADR-03 | 路径"实现核心功能"因不含 `code` 字样被派给兜底 Agent |
| 2 | 未评分时用 `quality_threshold` 充当分数 | 未评分返回 `None`，见 ADR-04 | 修改阈值即可让"分数"随之变化，证明其非评分结果 |
| 3 | `REPLANNED` 未纳入终止态 | 纳入 `TERMINAL_STATUSES`，见 ADR-05 | 存在失败任务时主循环退出条件永不满足 |
| 4 | L1 校验统一使用 `json.loads` | 按 `OutputSpec.kind` 分派，见 ADR-04/§3.6 | 代码与文档产物不是 JSON，L1 实际失效 |
| 5 | 重规划未定义下游依赖处置 | 改接至新子任务末端节点，见 ADR-06 | 旧任务停留在 REPLANNED，下游永远等不到 DONE，整链静默卡死 |

## 9. 需要决策的 3 项

### 🔴 D1：消息总线（Redis Pub/Sub）是否纳入本期？

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 不纳入**（当前设计） | 单进程直接调用，代码简单、易调试 | 失去"多 Agent 通过消息总线通信"的架构叙事；原技术栈承诺未兑现 |
| **B. 纳入轻量版** | 保留原设计叙事；契约广播有真实载体；为二期多进程预留 | 增加约 40h 工作量；调试复杂度上升；单进程下收益低 |
| **C. 抽象接口 + 内存实现**（推荐） | 定义 `EventBus` 协议，W1–W8 用内存实现，需要时换 Redis 实现 | 约 8h，几乎零风险，且保留了架构叙事 |

> **建议选 C**：在 `design.md` 中增加 `EventBus` 抽象层，当前用内存实现，Redis 作为可选实现写入二期。

### 🔴 D2：对比基线是否维持 3 个？

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 维持 3 个（原设计） | 简历数据最有说服力 | 复现 CrewAI + LangGraph 约需 40h，且极可能陷入调试 |
| **B. 单 Agent 必做 + 一个框架可选**（当前设计） | 工作量可控 | 说服力下降，容易被问"为什么不和成熟框架比" |
| C. 单 Agent + 一个框架（硬性） | 折中，可答"对比了主要竞品" | 约 20h |

> **建议选 C**：明确要求"单 Agent + 任选一个框架"，并在文档中写清选择理由。

### 🔴 D3：指标目标值回到原值还是保留调整？

| 指标 | 原值 | 当前值 | 建议 |
|---|---|---|---|
| 任务完成率 | ≥85% | ≥80% | 保留 80%（3 个基准任务上，85% 等同于 3 个全过，无容错空间） |
| Token 效率 | 降 ≥30% | 降 ≥25% | 保留 25%，但**须注明是基于 5 次重复的中位数** |
| 步骤效率 | ≤1.5x | 未定义 | **必须补定义**，否则五大指标缺一 |

> **建议**：完成率与 Token 保留调整值并在文档中写清调整理由；步骤效率必须补回定义。

## 11. 结论

> **方向正确，主干对齐，质量超出原设计，范围有缺口。**

三大创新点全部保留且实现路径更清晰；原设计中 5 处会导致实现失败的问题已被修正；
但 **Agent Memory、Eval 运行层、内置工具集、合并分解策略** 四块尚未进入当前设计。

这四项加上 D1/D2/D3 三个决策，应在 **W2 接口冻结之前** 完成，否则 W3 开始编码后会二次返工。
