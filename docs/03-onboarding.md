# 03 · 入门门槛

> 本文不是教程，而是**准入门槛清单**：达到即具备开始编码的最低能力。
> 协作规范、提交要求、求助方式见 [02-collaboration.md](02-collaboration.md)；Git 操作见 [01-setup.md](01-setup.md)。

- **适用对象**：全体成员（含负责人）
- **执行时限**：开工前 3 天内完成
- **完成信号**：在项目群回报「自测完成，10 题对 X 题」

---

## 0. 使用顺序

```
第 1 步：按第 1 节逐级对照自己的能力（L1 → L4）
第 2 步：做第 2 节的 10 道自测题（答案可展开核对）
第 3 步：有题不过 → 按第 3 节补课
```

**完成要求分两档**：

| 档位 | 内容 | 预计投入 |
|---|---|---|
| **最低要求** | L1 环境 + L4 协作 + 自测至少答对 7 题 | 半天 |
| **建议完成** | 再加 L2 Python + L3 项目理解 | 1–2 天 |

## 1. 能力基线

### L1 · 环境与动手（半天）

| 必须会 | 判定方式 |
|---|---|
| Python 3.11+ | `python --version` 输出 ≥ 3.11 |
| 装依赖 | 在新目录 `pip install pydantic openai jsonschema` 成功 |
| 跑通参考实现 | `python -X utf8 examples/quick_start.py` 输出 4 个成果物 |
| Git 基本操作 | 能 clone / 建分支 / 提交 / 推送（见 [01-setup](01-setup.md)） |
| 编辑器 | 能打开项目、跳转到定义 |

**Windows 必读**：项目含中文与符号字符，**缺少 `-X utf8` 会抛 `UnicodeEncodeError`**。
另：`PYTHONIOENCODING=utf-8 python x.py` 是 bash 写法，PowerShell 中会报错，统一用 `python -X utf8 x.py`。

**为什么要求跑通参考实现**：① 验证环境可用 ② 首次直观看到多 Agent 系统运行形态 ③ 建立团队共同语言。
它仅作参照，不作为开发基线。

---

### L2 · Python（1–2 天）

本项目 90% 的代码只用到以下 8 项，不需要更多。

| 必须会 | 掌握程度 | 用在哪 |
|---|---|---|
| 类型注解 | 能写 `def f(path: str) -> list[str]` | 全部函数签名 |
| Pydantic `BaseModel` | 定义模型、字段约束、`model_validate` | 全部数据结构 |
| `async` / `await` 阅读 | 能读懂，不要求会设计 | Agent 执行、工具调用 |
| 列表 / 字典推导式 | 能写 `[x for x in xs if x]` | 普遍使用 |
| 异常处理 | 会 `try/except/finally`，**知道不该写空 except** | 容错逻辑 |
| `with` 语句 | 文件与连接应使用上下文管理 | 沙箱读写 |
| f-string | `f"{a} 与 {b}"` | 日志与 prompt 拼接 |
| 建包 | 了解 `pyproject.toml`、`src/` 布局、import 生效条件 | 项目初始化 |

**验证方式**：写一个 30 行脚本 —— 定义含 3 个字段的 Pydantic 模型，用一段 JSON 校验它，字段不符时能报错。

**明确不需要掌握**：装饰器深层用法、元类、GIL、多进程、性能调优、`__slots__`、协程底层实现。

### L3 · 设计理解（2 天）

**这是「能参与讨论」的门槛，不是「能写代码」的门槛。** 未达到此级会导致实现放错位置，是返工的主要来源。

依据材料：[04-design.md](04-design.md) 第 1–4 章。

| 必须会 | 判定方式 |
|---|---|
| 说出完整流程的四步 | 分解 → 竞标 → 执行 → 验收 |
| 画出一次执行的链路 | 能白纸默画下方流程图 |
| 说明本模块的输入 / 输出 / 失败返回 | 不看文档能讲 2 分钟 |
| 说明本项目与现成框架的核心差异 | 一句话：现成框架的协作拓扑由人定义，本项目由系统自主决定 |
| 知道质量门控有三层 | 格式 → 语义 → 影响 |

**必须能默画的流程图**：

```
用户目标
   ↓
Planner        拆成子任务 + 依赖关系（DAG）
   ↓
Auctioneer     每个子任务广播，Agent 竞标，选一个
   ↓
Agent          中标者执行，产出成果物（Artifact）
   ↓
QualityGate    三层校验：格式 → 语义 → 影响
   ↓
通过入库          不通过 → 重试（最多 3 次）→ 耗尽则重规划
```

> **自测**：闭卷在白纸上画出上图，并标出本模块所在位置。画不出即未达标。

## 2. 自测题（10 道）

前 5 题动手，后 5 题口头作答。全部能答对即通过基础关。

### 动手题

**Q1** 在空目录建立 Python 项目，安装 `pydantic`，定义 3 字段模型并成功校验一段 JSON。
<details><summary>判定</summary>能独立完成（允许查文档）即通过；耗时超过 1 小时则回头补 L2。</details>

**Q2** 跑通参考实现，一共产出几个成果物？
<details><summary>答案</summary>4 个。</details>

**Q3** 那 4 个子任务是 LLM 拆分的吗？
<details><summary>答案</summary>不是。来自 `planner.py` 中写死的兜底模板（`_fallback_decompose`），因为未传入 LLM 客户端。这体现了本项目的核心模式：**LLM 主路径 + 规则兜底**。</details>

**Q4** 若出现 `UnicodeEncodeError`，首先检查什么？
<details><summary>答案</summary>是否遗漏 `-X utf8`。</details>

**Q5** 走一遍 Git 流程：建分支 → 改文件 → 提交 → 推送 → 开 PR。
<details><summary>判定</summary>PR 成功合并即通过。</details>

### 口头题

**Q6** 用一句话说明「质量门控」的作用。
<details><summary>答案</summary>在成果物入库前检查格式是否正确、内容是否达标、是否与已有产出冲突；不通过则退回重做。</details>

**Q7** 「重试」与「重规划」的区别？
<details><summary>答案</summary>重试是对同一任务再次执行（最多 3 次）；重规划是将任务拆解为更细的子任务并重新排入依赖图。</details>

**Q8** 本项目与 CrewAI / LangGraph 的核心差异？
<details><summary>答案</summary>现成框架的协作拓扑由人预先定义；本项目让 Agent 通过契约竞标自主决定分工。一句话：它们解决「编排便利性」，本项目解决「协作可靠性」。</details>

**Q9** 为什么不得直接 push `main`？为什么 `except: pass` 一律驳回？
<details><summary>答案</summary>前者：多人推同一分支会互相覆盖且无法审查。后者：异常被吞后只表现为「结果不对但无从定位」，这类缺陷排查成本最高。</details>

**Q10** 自行尝试 40 分钟仍无进展时，应当怎么做？
<details><summary>答案</summary>按三段式在群内求助：想做什么 / 试了什么 / 当前报错。避免只发「有人在吗」。</details>

## 3. 补课路径

| 缺什么 | 怎么补 | 最少投入 | 验证方式 |
|---|---|---|---|
| Python 语法 | 只补 L2 的 8 项 | 1–2 天 | 通过 Q1 |
| Pydantic | 官方文档 Models 章节 | 半天 | 能写 3 字段模型并校验 |
| 读不懂 async | 只需能读懂，不要求会写 | 半天 | 能解释 `async def` 与 `await` 的作用 |
| 不会建项目 | 参照 `pyproject.toml` + `src/` 布局搭一次 | 半天 | 自己的包能被 import |
| 不熟悉 Git | 走一遍 [01-setup](01-setup.md) 第三节 | 半天 | 第一个 PR 合并成功 |
| 看不懂设计 | 只跟一条链路：目标 → Planner → Auctioneer → Agent → Gate | 1 天 | 能白纸画出第 1 节 L3 的图 |
| 不理解 Agent | 记住一句：**Agent = 一个 while 循环，问模型 → 它说要调工具 → 你执行 → 结果回填 → 再问** | 1 小时 | 能向他人讲 3 分钟 |

**补课期间的三个原则**：不通读参考实现全部代码（按调用链读）；看教程连续超过 2 小时必须动手改一行；遇到不认识的语法只查该语法点，不试图理解整段代码。

## 4. 参考实现的正确用法

参考实现可运行，这既是优势也是陷阱。

### 三种正确用法

| 用法 | 做法 |
|---|---|
| **验收对照** | 自己完成模块后，对照它检查是否有遗漏环节（如超时保护） |
| **卡住时查做法** | 针对具体问题查看它的实现，例如工具调用结果如何回填 |
| **架构合理性验证** | 做设计决策时观察它的选择，判断本项目是否应当一致 |

### 三种错误用法

| 用法 | 后果 |
|---|---|
| 先读完它的代码再动手 | 实现会被其结构约束，等同于复制 |
| 遇到报错就整段粘贴 | 无法说明自己代码的行为，经不起追问 |
| 直接沿用其目录结构 | 无法写出决策记录，因为没有做过决策 |

### 硬性规则

> **先自己写，卡住了再看。顺序颠倒，本项目的学习价值即归零。**

若确实参考了某段做法，在 `docs/decisions/` 中记录：

```markdown
## 日期 · 主题
- 问题：我在纠结什么
- 参考范围：参考了哪一部分（具体到做法层面）
- 为什么：这是协议规定，还是设计选择
- 我自己的改动：在参考基础上做了什么调整
```

## 6. 最低限度常识（6 句）

1. **Agent = while 循环** —— 问模型 → 它说要调工具 → 你执行 → 结果回填 → 再问。
2. **合同网 = 谁派活、谁投标、谁中标** 的规则。
3. **本项目与现成框架的差异 = 协作拓扑由人定义 vs 由系统自主决定。**
4. **span = 为每段操作记录开始 / 结束 / trace_id**，串联成树。
5. **模型不自评** —— 属于 LLM 校准问题，需由另一模型或历史数据评判。
6. **按模块分工，阶段只作里程碑** —— 每人长期负责一块，不做全员轮换。
